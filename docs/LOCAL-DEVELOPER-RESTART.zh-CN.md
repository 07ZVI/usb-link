# 本地开发者远程重启

本地调试构建的开发者调试总开关同时控制 USB 远程重启入口，不增加独立开关或界面按钮。只重启 USB Link，不重启 Windows。USB 升级安装继续使用原来的管理员确认。

Mac 开发工具使用 `--restart` 请求重启，使用 `--restart-status` 读取结果；两者只允许附带可选的 `--connection`，不能与安装、签名、档案收取混用。默认重新发现当前 USB 通道，沿用固定地址、TLS 证书绑定、令牌及 USB 代次验证，不使用旧连接凭据跨代重试。

请求只包含随机编号。Windows 为当前已验证的安装及交互用户创建无触发器的临时任务，运行固定辅助入口；不接受任意路径或命令，不改变开机启动选项，也不修改 UAC 策略。同名但不符合记录的任务不会被覆盖或删除。

辅助程序使用既有核心退出协议，等待连接停止及原值恢复，再通知已登记的旧登录界面结束。它持有每个已验证界面进程的身份与句柄，必须观察到它们真正退出，才提交核心退出并等待确切旧核心进程结束。随后启动相同的受保护安装，验证新核心的版本与状态，并请求打开登录界面。整个重启使用既有管理员后台与当前用户权限，不需要再次确认管理员权限。恢复失败时不进入重启阶段；启动阶段失败会保留失败状态，不能以请求已发送代替成功。

`prepared` 只表示请求排队；`completed` 要求新核心通过身份和状态验证，且固定界面启动已请求。`login_requested` 不证明窗口已经显示，`core_readable` 不证明 iPad、串流或 LocalSend 已经恢复。USB 通道在退出阶段断开属于预期行为，Mac 工具不会因丢失请求确认而自动重复重启。

关闭开发者调试会撤销尚未获准的请求，并阻止新请求。已经获准的单次重启通过受保护的一次性记录完成交接，不要求已经关闭的旧 USB 服务器继续存活。任务清理失败、进程身份不明或记录变化会明确保留失败状态；不强杀进程或采纳未知任务。正式公开构建排除这项执行能力。

源码、回归与打包检查不代替 Windows 原生任务、真实退出耗时或重新连接验收；这些分别由本地实测记录确认。

0.10.50 首次实测在辅助任务准备阶段失败，尚未停止原程序；旧状态只保存通用任务错误，不能确认注册、读取或执行中的具体失败点。0.10.51 为这些阶段分别保存固定操作名、阶段、失败谓词位和原生数值错误码，首次失败与后续清理失败独立保留。失败任务的状态查询只在内存中检查固定名称，回传布尔与枚举摘要，不回传任务 XML、账户、路径或异常正文，也不据此采纳任务身份。

Windows 将任务用户表示为账户名称时，仅在系统解析出的 SID 与原已验证安装所有者完全一致后接受。旧失败任务若没有已验证指纹、没有辅助进程且从未获准执行，原受保护记录另行保留，最多十六份；未知任务不删除，新请求使用新编号，旧辅助任务仍须匹配当前一次性记录。以上兼容与诊断改动尚不能作为首次失败根因或远程重启成功的证明。

0.10.51 实机只读检查确认旧任务存在、名称及路径一致、已启用、用户 SID 一致；失败位仅为 `AllowStartOnDemand` 与 `Enabled`，并非用户身份不匹配。原检查逐字要求这两个 XML 字段为 `true`，但微软 [Task Scheduler Schema](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-schema) 将二者定义为可省略、默认 `true`。0.10.52 按这两个已知默认值读取，显式关闭仍拒绝；不得由此放宽其他策略、用户、固定命令或原始任务 XML 指纹核对。位图本身没有保存字段原文，尚不能区分原 XML 的缺省和其他合法布尔表示；完整重启及实际退出耗时仍需实机结果确认。

0.10.52 实装后，同一旧任务的失败位已降为零，两次请求均完成旧核心退出和新核心身份、状态验证。但用户第二次观察到三个图标及两个主界面，证实只重启后台不足以完成整程序重启。0.10.53 增加受认证的登录界面登记，同一用户及会话只接纳一个实例，重复打开请求唤起原界面；核心更换后重新登记，短暂断线不会被当作退出指令。

远程重启只有在恢复就绪后才发送 `close_followers`，界面代理先等待自己持有的渲染子进程结束，再退出；辅助程序及核心提交入口分别检查 `ui_drained`。普通手动退出保持原提交协议，窗口关闭仍缩至托盘。升级引导进程若遇到已登记的界面，仍须完成原有安装验证，不能把重复实例当作安装成功；安装期间的已验证退出交接也继续保留。旧版遗留窗口的清理及新版单实例效果必须实测，不能仅据登记表判定。
