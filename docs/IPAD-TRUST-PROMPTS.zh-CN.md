# iPad 重复“信任此电脑”提示调查

调查日期：2026-10-15。范围：当前普通 iPad 连接路径、保留的旧源码历史和历史反馈；未操作用户设备。

本次用户确认：两次均为 iPad 系统的“信任此电脑”，第一次选择“不信任”。

## 结论与边界

当前连接流程不主动发送配对请求，也不为连接建立 Apple 配对会话。它会切换 USB 网络模式；首次需要调整 Windows 设备分组时，还可能重启 USB 父设备并重新激活网络模式。这些重新枚举操作是重复提示的候选触发条件，不能仅凭源码认定就是本次两次提示的原因。

保留的 0.8.87 实机反馈已明确记录过重启后两次信任提示。此前 0.8.84 的成功反馈提到出现提示，但未独立记录精确次数。因此，现有证据支持此现象至少在 0.8.87 已出现，无法确定首次出现版本，也不能否定用户其他连接过程只提示一次的观察。

Apple 说明：选择“不信任”后，每次连接会再次提示；它没有承诺一次物理插拔只提示一次。参见 [Apple 官方说明](https://support.apple.com/en-au/109054)。该说明不能单独证明 USB 模式切换必然触发第二次提示。

## 已核对的源码与版本变化

- `internal/app/launcher/main_windows.go` 的 `executeMode` 走 `RunNetworkOnlyAppleControl`，不暂停或重启 AMDS。
- `internal/app/ipadncm/check_windows.go` 在已处于活动网络配置时直接返回；否则核对初始模式与本次许可后，只发送一次 `SET_MODE` 请求，并最多等待 8 次、每次 1 秒的重新枚举观察。
- 首次无可复用分组且原生驱动启动失败时，连接流程可进入分组配置，重启 USB 父设备，再次检查并按需切换模式。已有分组验证成功后使用 `CONFIGURATION_REUSED_NO_WRITE_OR_RESTART`，不为复用而重启设备。
- 在旧源码提交 `d3fca36` 之前，上述模式切换、分组重启与重新激活路径已经存在。该提交没有新增第二次切换；相关行为变化是恢复旧 AMDS/WPD 隔离设置，并取消连接期间的服务暂停。它与历史现象时间接近，但不是已证明的因果关系。
- 公共源码起点 `eb0cf53` 到调查时 `381153d`，上述模式切换和分组调用链未新增第二次调用。安装、驱动状态或其他 Apple 软件是否改变了实际执行分支，需要当次设备证据。

## 最小实机核对

保持当前信任和服务设置不变。完成一次正常插线连接，期间不手动点击重新连接；记录两次提示各自出现的时间，以及第一次选择的是“信任”还是“不信任”。连接成功或失败后立即导出该次诊断。

检查诊断中的以下证据：

- `ncm_check.set_mode_attempted`、`ncm_check.ncm_descriptors_appeared`：本次是否发出了模式切换并观察到网络配置。
- `temporary_grouping_trial.trial_restart.target_restart_attempted` 及 `mode_reactivation.set_mode_attempted`：是否实际经历了分组重启和第二次模式切换。
- `temporary_grouping_trial.transaction.status`：是否复用了既有分组而未重启。
- `resident_monitor_observations` 的连接尝试、自动重试、手动重试和阶段记录：是否同一次插线进入了多个连接尝试。

本次增加的 `usb_mode_switch_begin/end` 使用现有软件尝试计时，覆盖真实模式请求及随后的重新枚举观察。它不记录设备序列号、配对内容或 iPad 界面，也不把 Windows 设备通知计数当作物理插拔次数。失败和取消仍按原有结果返回；结束事件只表示操作返回，成功与否仍查该次模式结果。缺失或被环形缓冲区淘汰的事件不能当作操作未发生。

Mac 会话运行时，现有 5 秒诊断循环会将精简 iPad 内存快照独立写入 `service.log` 的 `USB_LINK_UPGRADE_EVIDENCE` 行，并携带 `core_version`。状态变化时写入；无变化时每 30 秒补写，避免升级短暂断网错过首条状态。失败写入不更新去重记录，下次循环重试。每条最多保留 12 个相关阶段，分别注明筛选截断和源缓冲区遗漏，不包含持续增长的时钟、自由错误文本或设备标识。日志轮转和采集间隔仍可能遗漏事件，日志中的历史会话标记及旧采样时间不能当作当前连接证明；此通道不增加设备查询或远程服务。

如果诊断只有一次模式切换、没有父设备重启或连接重试，仍出现两次提示，应继续检查 Apple 软件的访问或备份行为及实际 USB 断连情况，不能为了消除提示直接修改配对、隔离服务或放宽设备核验。

## 已有分组但记录缺失

0.10.14 的设备日志确认了一种独立阻断：系统已有 `EnumeratorClass=020000`，两个 NCM 控制节点中一个启动、另一个失败且没有游离数据节点，但当前根设备的配置记录与 pending 均不存在。目录盘点有截断，不能据此断言整个目录没有其他记录，也不能断言升级删除了记录。

0.10.15 对这种现存布局使用独立验证路径。它重新检查当前授权、物理设备和原生父链、官方驱动绑定、完整控制节点结构及唯一运行中的网卡；验证失败时停止，不回落到首次分组写入。该路径不构造分组恢复记录、不写分组注册表、不重启设备，也不宣称拥有原值。随后仍通过既有对端验证、地址配置与网络资源清理检查，不能把通过布局检查当成网络或串流已成功。

本地诊断版另有独立只读网络采样，每轮完成后等待 10 秒，连接失败也继续。缓存包含采样时间、过期/预算标记及限定 iPad 网卡的 IPv4 信息；默认应用端口观察不证明进程身份、实际路由或应用成功，目前不观察 IPv6。它以 `ipad_runtime_network` 独立日志行回传，连接与配置记录仍在 `ipad_connection` 中。开发者开关仅控制详细信息显示和导出，不控制这项自动采样。

## 0.10.16 本地诊断时间线

本地构建新增独立的 `ipad_trust_timeline` 回传段。每次进程启动生成运行标识，记录 UTC、观察器启动后的单调毫秒数和软件连接尝试编号。只读观察器在连接失败后仍运行：每秒采样 PnP 节点和 Apple Mobile Device Service 状态及 PID，并接收合并后的 Apple 设备通知提示。每类采样保留最后完成时间；读取失败明确记录错误类别，不能解释为设备不存在或状态没变。原生调用可能阻塞，因此一秒是目标采样间隔，不是严格时限。

设备通知仅是收到通知的提示，不能当作物理拔插、完整重新枚举次数或系统弹窗记录。服务状态与 PID 变化也不能证明发送了配对请求。普通连接的模式切换、分组写入、设备重启等已有操作窗口同时进入该时间线；观察器自身不发 USB 控制请求、不配对、不修改驱动或服务。

开发者诊断界面增加“第一次”和“第二次”信任提示标记。用户看见提示后点击，记录的是后台收到手动标记的时间，包含反应及传输延迟。它不能自动读取 iPad 屏幕，也不代表后端已经确认弹窗来源。时间线明确保留 `ipad_prompt_observed=false`、`pairing_request_observed=false`。

时间线最多保留 20 个事件和 4 个节点摘要，并报告淘汰及通知抑制计数。三类证据分别回传，服务日志采集尾部增至 48 KiB；单条仍限制 8192 字节，整体诊断仍限制 256 KiB。环形缓冲区、日志轮转与采样间隔仍会遗漏瞬时事件。建议安装时先拔下 iPad，保留 Mac 与 Windows 连接，确认观察器启动后再插入，以捕获连接前的基线。

## 0.10.16 实机结果与 0.10.17 标记修正

0.10.16 的插线前基线及两轮插线均已通过 USB 通道读取。每轮仅观察到一次模式切换，随后 PnP 根节点短暂消失并以两个 NCM 控制节点重新出现；AMDS 采样的状态与 PID 未变化。第一轮最终完成地址分配和对端验证，后台进入 connected。用户报告两次信任提示，但这些观察仍不能证明弹窗的直接请求来源。

用户在第二轮点击了手动标记，但日志没有收到。源码检查确认遗漏了后台服务动作允许列表：桌面发送与普通 UI 处理已经接通，服务代理入口却返回 CORE_ACTION_UNSUPPORTED。0.10.17 将两个精确动作加入仅本地诊断构建开放的服务允许列表，并增加服务入口引用及本地/公开构建、未知动作的回归检查。旧的界面烟测仅验证发送端，不能证明安装后的服务往返已成功；新包仍需实机验证标记到达。

## 0.10.18 临时 Apple 服务对照

用户已明确允许一次临时服务对照，并知悉会中断 iTunes / Apple Devices 对移动设备的同步或备份。仅本地诊断构建提供固定“开始”与“取消并恢复”动作，不因安装或打开开发者开关自动执行，也不作为普通连接默认策略。

该对照复用原状态恢复记录：暂时停止 Apple Mobile Device Service，等待同一 iPad 拔下并重新接入，再执行已授权的网络模式检查。测试预算 110 秒，恢复预算另 10 秒；原生系统调用阻塞或服务启动失败时不能承诺硬性 120 秒内恢复，必须报告恢复失败并保留恢复记录。恢复后的服务状态和启动类型需核对，恢复未确认时普通 iPad 流程继续暂停。此流程不修改服务启动类型、不配对、不删除配对记录。

新增 `usb_control_open` 与 `usb_get_mode` 起止事件，区分打开控制通道、读取当前模式与真正 SET_MODE 请求。此前 `usb_mode_switch_begin` 紧贴 SET_MODE，因此不能用旧时间线排除其之前的控制通道访问。`apple_service_trial` 随时间线回传紧凑的当前测试与恢复结果。普通服务运行下的基线已保存，此对照用于区分服务参与程度；不能仅凭服务状态或提示次数便宣称已永久解决。

## 0.10.26 同版本时序对照

既有普通连接记录中，从每秒采样首次看到设备到模式切换开始，双提示轮为 11,284 ms，后续单提示轮为 1,925 ms；两轮模式操作窗口分别为 2,052 / 2,053 ms，后续原生启动检查均为 10,094 ms。差异主要出现在软件连接尝试计时开始前。两轮之间 AMDS 已重启，因此这些记录只能支持时序假设，不能证明弹窗被覆盖或等待时间就是根因。

本地开发者调试增加两个持续开关：快速检测将等待新设备时的缓存 PnP 兜底从 30 秒改为 1 秒；延迟切换对照要求快速检测已开，并在接受候选前额外等待 12 秒。延迟结束重新读取同一候选，随后仍走原有设备身份和授权检查。设置按已验证安装所有者独立保存，没有有效期或单次限制；开发者总开关关闭时停用，再开启时恢复保存的选择。此对照不停止或重启 Apple 服务，不改变当前运行中的网络会话。

`connection_timing` 独立回传 owner 等待、唤醒原因、候选接受、连接尝试起点及原生通知线索，并与信任观察器共享运行标识和单调时钟。未观测时间用 -1；通知计数为进程累计的合并线索，不是 USB 重新枚举或弹窗次数。它不占用信任时间线的 20 个事件槽，但仍共用滚动日志，需在每轮后持续保存采集结果。

对照次序为快速、延迟、快速，AMDS 保持运行且不改变服务设置；每轮保持相同插拔和解锁条件，信任提示选择“不信任”，由用户报告实际次数。必须同时核对本轮真实模式切换时刻和服务 PID；若未观察到预期时序差异或服务状态改变，不能把提示次数差异归因于该开关。实验结果需独立记录，不因编译或开关保存成功宣称双提示已修复。

## 0.10.27 重启后调试入口修复

0.10.26 在升级后确认调试设置恢复，但 Windows 重启后用户报告调试“尚未就绪”。USB 实测核心和桥接均为 0.10.26，桌面状态持续读取成功，但 `developer_debug` 为未初始化的零值，`connection_timing.persistence` 为 unknown。源码确认远程管理器构造失败会跳过整个本地调试接线；原错误只写 stderr，本轮回传未包含具体失败阶段。因此尚不能认定是哪一步原生清理失败，也未开始快速、延迟、快速的设备对照。

本地版本将可恢复的网络清理与本地诊断分离，清理全部成功前 USB 安装保持关闭。严格的存储、所有者和授权错误继续阻断安装，并在诊断中显示失败阶段。另将初次明确初始化响应显示为等待状态，并移除组件齐全时每次打开都会出现的准备窗口。编译与模拟检查不代替 Windows 重启后开关恢复、窗口消失及 iPad 提示次数的实测。

## 0.10.27 重启与时序对照实测（客户端日期 2026-10-16）

用户报告两次重启后连接表现不同，包含首接暂停、重插后恢复，以及信任提示为零次或一次的非受控观察。当前实机回传确认核心与桥接均为 0.10.27，开发者调试和快速检测均已从保存设置恢复。首次初始化错误已定位到本地防火墙清理阶段，后续清理完成，USB 推送通道就绪。原生错误未提供更细的操作码，因此不把该阶段进一步归因为某个 Windows 服务。

同一观察进程 `c19d2a28e09a0c7d01eb96ce` 内，AMDS 持续 Running(4)、PID 3644，没有执行服务对照。延迟轮 attempt 8 的候选等待为 12,001 ms，首次根节点采样至 SET_MODE 为 13,980 ms；用户报告两次信任提示，网络连接成功。关闭延迟后的 attempt 9 从后台接受候选到 SET_MODE 为 598 ms，首次根节点采样至 SET_MODE 为 597 ms；用户仍报告两次提示，第一条短暂出现后被打断，约 1–2 秒后出现第二条。后一轮后台也确认 DHCP 与 IPv4 往返正常。

这对受控结果不支持“仅缩短 owner 等待即可稳定消除双提示”。更早的零次或一次提示观察没有逐轮固定条件，不能覆盖本轮反向复测。第一条被打断与模式切换、设备重新枚举的时序相符，但现有日志不观测 iPad 弹窗或配对请求，不能确认弹窗覆盖机制或请求发起进程，也不能保证进一步加速能得到零次提示。iPad 的“允许配件连接”由用户确认是系统提示，需与“信任此电脑”分别记录。

首次暂停的最终错误未在当前回传日志中保留，仍未定位。中间原生启动检查的一个 NCM 控制节点 problem 10 与另一个网卡正常工作可以同时存在，不能直接当作最终连接失败。源码另有两个待改进点：无 receipt 的现有布局会等满 10 秒后才核验唯一可用网卡；完整的最近八次尝试历史目前仅在本地诊断 ZIP 中，未进入 USB 紧凑回传。后续调查应保留失败轮最终阶段和错误，不能用提示次数代替网络就绪证据。

本地证据：`.local/evidence/20261016-upgrade-ipad/0.10.27/timing-controlled-comparison.json` 及相邻 `intermittent-replug-report`、`timing-delayed-*`、`timing-fast-return-observation` 目录。当前保留快速检测开启、延迟对照关闭。

## 2026-10-17 外部资料与本机历史交叉核对

### 可以确认的机制

Apple 的[物理配对安全说明](https://support.apple.com/zh-cn/guide/security/secadb5b6434/web)将信任定义为主机发起的配对及后续受保护内容访问。网络模式请求和内容配对是不同操作，不能把“不信任”解释为必须禁止 NCM 网络，也不能从信任窗口倒推出请求进程。

上游 usbmuxd 的[模式切换提案](https://github.com/libimobiledevice/usbmuxd/issues/205)明确说明切换后设备会重新连接；其 [preflight 源码](https://github.com/libimobiledevice/usbmuxd/blob/master/src/preflight.c#L237-L247)明确在未配对时主动调用 `lockdownd_pair` 触发信任窗口。该源码证明重新发现设备后主动请求信任是一种真实实现机制，不能把开源实现当成 Windows AMDS 的内部实现证据。上游 `--no-preflight` 也不是已知的 AMDS 配置选项。

本机 0.10.17 的两次人工标记分别位于唯一一次 SET_MODE 前后；0.10.22 首次标记比控制通道打开早 10,128 ms。当前源码在已活动 NCM 时直接返回；一次模式控制调用发送 SET_MODE 后立即进入观察并返回，没有重发循环。首建分组可能另有父设备重启及模式恢复，但本轮复用已有分组的双提示记录没有该路径。因此当前首要解释仍是初次枚举和模式切换后的再次枚举，各自给内容访问组件提供了触发提示的机会；请求源和 iPad 的提示保留状态仍未直接观测。

### 照片导入接口是具体候选，但此前隔离并未完整验证

同类 Windows 项目 [iphone-usb-reverse-tethering-windows](https://github.com/0xbaksa/iphone-usb-reverse-tethering-windows#what-actually-stood-in-the-way-windows)报告 WPD/PTP 照片访问会触发信任，停用该子接口后可零提示联网；[实际脚本](https://github.com/0xbaksa/iphone-usb-reverse-tethering-windows/blob/main/USB-Share.ps1#L66-L74)只选择 `MI_00` 的 WPD 节点。该项目声明只验证一款 PID 12A8 的 iPhone 和一组 Windows/iOS 环境，不是本机 PID 12AB iPad 的验收结果。其移除 AppleLowerFilter、安装 libusb 过滤器及修改配置索引的做法不作为本项目修复方案。

本机历史描述符确实包含 PTP：cfg3 的 interface 0 为 06/01/01，Windows 绑定 WUDFWpdMtp；cfg5 保留另一实例的 MI00。0.8.81 的原始证据显示 cfg3 的 MI00 曾启用；实际禁用并取得恢复记录的是 cfg5 带 REV_1316 的另一个 MI00 实例。随后冷插 attempt 6 在 108–1352 ms 的九次阶段采样中，当前便携设备集合均为空，没有执行新的禁用；稍后状态仅核对已登记的 cfg5 实例。用户仍报告需要点击“不信任”，证明至少一次提示，不能据此声称已经排除了完整 PTP 隔离方案，也不能反过来认定 cfg3 实例就是原因。

原始材料：`.local/evidence/0869-hardware/0881-after-user-unlock-native.json`、`0881-cold-phase-progress-native.json`、`oct08-A-0881-I7-cold-entry-readonly-final.json`、`oct08-A-0881-historical-cfg3-ptp-readonly.json`。这些历史实例和摘要不构成修改当前设备的授权或身份凭据。

### 改法优先级与验收条件

优先验证当前 iPad 的 PTP 访问通道，而不是继续只改变发现延迟。应先明确记录同一物理设备在 cfg3、cfg5 下的 MI00 和 MI01 实例、驱动类别、启用状态及替换时刻；当前紧凑时间线把两者归为 other，不能完成该区分。若做隔离对照，应为单一持续开关，保存每个实际修改实例的原状态，关闭后恢复；只针对本 iPad 照片子接口，不能宽泛匹配所有 Apple、WPD、WinUSB 节点或禁用复合父设备。启用期间 Windows USB 照片导入将不可用，需要在界面明确说明。持续开关不能靠事后一次空枚举宣称隔离成功，也不能保证阻止开关生效前已经发出的信任请求。

验收必须在相同服务状态下比较开、关、再开，并包含电脑重启后的首次连接、短时与较长断开后的重连。分别记录信任次数、配件许可和后台模式切换次数，核对 DHCP、IPv4 往返以及 Wi-Fi 关闭后的 Moonlight 和 LocalSend。若仍有提示，再区分 AMDS/mux 访问与 PTP，不能默认全局停止 AMDS。目标是稳定减少到一次并评估零次，当前尚未实现或验收该改法。

另有上游 [mode 5 支持提交](https://github.com/libimobiledevice/usbmuxd/commit/df80b73b411d1053cb87e96439d2282879d9baa8)，说明 iOS 17 起的 CDC-NCM Direct 模式不暴露 usbmux/PTP。它不是现有 mode 3 的无风险替代：[原始研究](https://www.synacktiv.com/en/publications/ios-a-journey-in-the-usb-networking-stack)区分普通反向共享 NCM 与 RemoteXPC 私有 NCM，后者可能缺少 Windows 驱动需要的中断端点。本机 mode 5 的端点、驱动、DHCP/IPv4 行为和恢复均未验证，不能为了消除弹窗直接更改模式白名单或发布。

本轮没有改变 Windows 服务、设备、驱动、配对或连接策略，也没有生成新版。通过现有 USB 通道尝试只读采集时，本机诊断绑定地址不在，得到 `EADDRNOTAVAIL`，没有取得新的 Windows 状态。

## 0.10.28 本地照片接口隔离候选

开发者调试新增单一“照片介面隔離”持续开关，首次默认关闭，没有有效期。独立的所有者设置保存选择，不构成设备授权。开发者总开关关闭时撤销隔离意图并恢复本功能修改的节点，重新开启时读取原选择；界面分别显示保存、实际隔离及恢复结果。

普通连接仍先核对当前设备身份和实际授权。仅网络模式路径随后绑定同一 iPad 的私有根实例，在模式切换前和确认同根 NCM 重新枚举后同步扫描，并以独立串行 worker 每秒继续检查，处理晚出现和替换的照片节点。只允许同一原生父链下 PID 12AB、MI00、WPD/Image 类及照片服务的精确实例；不修改复合父设备、MI01、网卡、AMDS 或配对，也不新增模式请求。空扫描显示等待照片接口，不作为隔离完成证明。操作系统调用可能超过目标采样间隔，不能承诺赶在首次信任请求之前。

每次首次禁用前，把精确实例和原 ConfigFlags 值及属性存在性写入独立保护恢复记录并读回；原本已禁用的节点不接管恢复。关闭开关、关闭开发者调试、正常结束核心进程时恢复本功能实际修改的节点。进程再次启动先处理未结记录；卸载和公开构建也只允许恢复这些记录，不能创建新的隔离。恢复失败保留记录并显示 pending，不能把开关已关闭显示为原状态已恢复。启用期间该 iPad 的 Windows USB 照片导入不可用。

USB 日志新增独立 `photo_isolation` 段，并保留到有界传输的最新证据集合；服务日志尾部增至 64 KiB，以容纳五个独立证据段，整体传输仍限制 256 KiB。隔离状态携带观察时间、同运行单调时钟、固定失败阶段、具体原因及 CONFIGRET/WIN32 原生数值码，不输出原生自由文字或设备身份。现有信任观察器区分 MI00、MI01 与照片服务，四个节点槽优先保留根节点、照片节点、Apple 控制节点及健康 NCM，额外节点仍明确计入省略数。日志继续不观测 iPad 屏幕或实际配对请求。

此候选用于验证内容访问通道是否导致重复信任提示。构建、模拟和代码检查通过也不能代替 Windows 重启、真实提示次数、Moonlight 与 LocalSend 的设备验收。

### 0.10.28 实机观察（客户端日期 2026-10-17）

安装后、照片隔离关闭时，用户连续两轮报告零次信任提示；第二轮也没有配件许可提示。第二轮根节点从缺席到返回的采样间隔为 179 秒，程序仍执行一次模式切换，随后照片接口启用，AMDS 状态和 PID 不变。保留的隔离状态均为关闭，没有隔离请求或本功能接管的节点。这说明零提示并不依赖此开关，模式切换本身也不是弹窗的充分条件。该轮用户只确认界面显示连接成功，没有测试 Moonlight 或 LocalSend；后续设备消失由用户确认是拔线。

之后隔离关闭的两次重连均出现配件许可，信任提示分别为零次、一次。用户开启照片隔离再连接，仍报告两次信任提示。回传确认 `photo_isolation.effective=true`、`phase=isolated`，一个同根 MI00 照片节点禁用，PnP 为 problem 22；本轮只有一次模式切换，地址分配和 IPv4 对端验证通过。应用通信尚未验收，日志也没有 iPad 弹窗的精确时刻，不能证明隔离早于两次提示，更不能推定初始枚举的每个实例都已提前隔离。

当前实现不能作为可靠消除信任提示的方案；配件许可与信任提示分别保留计数，照片隔离仍默认关闭。原始记录保存在本地证据目录，不纳入公开源码。
